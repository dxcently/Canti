# firmware: the Pico 2 W

The device half of VOX. It listens through an I2S MEMS mic (INMP441), turns each sound into a VOX line with the on-device extractor (`extract/`, a C++ port of `extractor/vox_extract`), and sends it to the phone over Bluetooth LE, as specified in [PROTOCOL.md](../android/PROTOCOL.md) "BLE GATT link (v1)".

`vox_node` has:
- the full BLE link (LE Secure Connections bonding with a 60 s pairing window, fragmentation, the app commands);
- the one button, sleep and wake (Bluetooth and mic off), and the blue status LED;
- mic diagnostics;
- **the on-device extractor** on core 1: every sound the mic hears goes out as a feature message with its fp1 `features` (see [On-device extractor](#on-device-extractor)). checked on this PC against the Python extractor, and **on the Pico 2 W** (2026-09-26: all 19 vectors through `ext feed` equal the reference, times exact), see below. Not yet heard through a real mic;
- **canned test sounds**: real extractor lines, generated at build time by running the Python extractor on its synthetic test clips, and sent on command.

Wiring the breadboard: [HARDWARE.md](HARDWARE.md).

## Build, flash, test

```bash
cd ~/VOX/firmware
PORT=$(ls /dev/serial/by-id/usb-Raspberry_Pi_Pico*-if00) tools/build.sh --upload   # extractor → test_sounds.h, compile, flash (secure build)
tools/build.sh --insecure --upload      # debug build: no encryption, INFO says "insecure":true
tools/build.sh                          # compile only; --no-gen skips the extractor step

PY="nix shell --impure --expr 'with import <nixpkgs> {}; python313.withPackages (p: [p.bleak p.pyserial])' -c python"
eval $PY tools/ble_check.py             # full BLE test, about 7 minutes (four 60 s timeouts); --quick: about 2 minutes
eval $PY tools/pico_stream.py -s 5 -o /tmp/mic.wav     # record the mic
PICO=$(ls /dev/serial/by-id/usb-Raspberry_Pi_Pico*-if00)       # the Pico's own port; /dev/ttyACM0 may be a phone
stty -F $PICO 115200 raw -echo && cat $PICO &   # plain console; type with: echo status > $PICO
```

- **Flashing.** `--upload` sends `bootsel` over the serial port and then flashes with `picotool`. The arduino-cli default fails on this machine: it needs `udisksctl` to mount the RP2350 drive. A blank board, or one whose firmware hangs, needs BOOTSEL held while plugging in. Then run `nix run nixpkgs#picotool -- load -x build/vox_node/vox_node.ino.uf2`.
- **The extractor step** runs `~/VOX/extractor/run python tools/gen_test_sounds.py`. It only reads `extractor/`. It fails, and writes nothing, if the extractor no longer gives the expected label for a test clip. `--check` exits 1 when the lines or the vocabulary changed.
- **Re-flashing erases bonds.** BTstack keeps its bond store inside the program image, so every flash forgets the phone. Remove "VOX-XXXX" from the phone's (or PC's) Bluetooth list, hold the button 5 s (pairing window), then connect again. Otherwise the link fails with a re-encryption error; the serial console says so. `ble forget` erases the bonds without flashing.
- **BlueZ (PC) pairing needs an agent.** Without one, BlueZ rejects the Just Works confirmation (SMP reason 0x0c). `ble_check.py` registers its own for the run and removes the bond at the end (`--keep-bond` keeps it). With `bluetoothctl`, run `agent NoInputNoOutput`, `default-agent`, then `pair <address>`.
- **Serial console:** 115200 baud (any baud rate works over USB). Commands end with a newline and are echoed as `> cmd`.

**USB permissions (NixOS).** Flashing and the serial port need access to Raspberry Pi USB devices (vendor `2e8a`). A temporary rule in `/run/udev/rules.d/70-vox-pico.rules` gives the `users` group access until the next reboot. To make it permanent, add this to the NixOS config and rebuild:
```nix
services.udev.extraRules = ''
  SUBSYSTEM=="usb", ATTR{idVendor}=="2e8a", MODE="0660", GROUP="users"
  SUBSYSTEM=="tty", ATTRS{idVendor}=="2e8a", MODE="0660", GROUP="users"
'';
```
For about 2 s after a flash, `/dev/ttyACM0` shows `root:root 0600` until udev applies the rule. That is expected.

The Arduino IDE also works (`nix run nixpkgs#arduino-ide`). In it, add the board URL from `arduino-cli.yaml` under Preferences → Additional boards manager URLs. Then pick "Raspberry Pi Pico 2W" and set Tools → IP/Bluetooth Stack to "IPv4 + Bluetooth".

## Pins

| Signal | GPIO | Physical pin | Goes to |
|---|---|---|---|
| The button | GP14 | 19 | button → GND (internal pull-up) |
| Bluetooth LED (blue) | GP13 | 17 | 100 Ω → LED anode (long leg); cathode → GND; active high |
| Mic BCLK (SCK) | GP18 | 24 | INMP441 SCK |
| Mic WS | GP19 | 25 | INMP441 WS |
| Mic data | GP20 | 26 | INMP441 SD |
| 3.3 V | 3V3(OUT) | 36 | INMP441 VDD. **3.3 V only; never 5 V (VBUS pin 40, VSYS pin 39)** |
| GND | GND | 3, 8, 13, 18, 23, 28, 33, 38 | INMP441 GND and L/R, the button, the LED cathode |

GP11, GP12 and GP15 (pins 15, 16, 20) are free: earlier drafts had an RGB LED and a second button there.

The I2S format is 16 kHz, 64 BCLK per frame (32-bit slots, left channel), with 24-bit data from the INMP441. GP20 has a pull-down, so a missing mic reads as all zeros. INFO then says `"mic":"none"`.

## The button, sleep and wake

> **Verified on hardware (2026-09-26), except bonded reconnect.** On the Pico, the button logic (`btn click`, `btn clicks 3/5`, `btn hold 1200`, `btn hold 5500`) gives the console lines of HARDWARE.md step 3, and sleep no longer hangs (`ble_power_off()` waits for `HCI_STATE_OFF`; an 8 s watchdog is the backstop). **Wake did not bring Bluetooth back** when it powered the radio before the mic: the CYW43 SPI bus then got the PIO state machine and DMA channels I2S had used before the sleep, and on those it never comes up (`hci_power_control(ON) returned -6`, BLE stuck at `starting`, and each failed wake keeps a state machine and 2 DMA channels). Releasing and retrying lands on the same ones and fails the same way (tested: 3/3 attempts, 3 wakes); on resources I2S never used it works every time (tested: 7 wakes). `wake()` now starts the mic first, as `setup()` does, so each side gets back what it had at boot. `status` prints a `hw:` line (claimed PIO state machines, DMA channels, free heap): a sleep/wake cycle must leave it unchanged. Verified on that build (2026-09-26): 10 sleep/wake cycles (console and button alternating), each advertising again (the radio up in 0.83 s, VOX-2807 seen by a PC scan), the `hw:` line equal to the boot baseline after every cycle (heap: one 8-byte allocation on the first wake, then constant), everything released while asleep, and the 60 s no-phone timeout. Still to do: bonded reconnect after a wake, and a full `tools/ble_check.py` run.

One button, as in PROTOCOL.md "The button":

| Press | Awake | Asleep |
|---|---|---|
| 5 quick presses | armed: turn off (disarm, the `sleeping` message, sleep). Not armed: arm | wake; arm once a bonded phone subscribes |
| 1 click | gesture ⇄ cursor mode | nothing |
| hold 1 s | disarm at once, while still held (the fast stop); sleep on release | nothing |
| hold 5 s | disarm (at 1 s), then open the 60 s pairing window instead of sleeping | wake and open the pairing window |
| 2–4 presses (6 or more too) | nothing | nothing |
| held while plugging in | the **test-sound trigger**: from then on, 2 presses send the next canned sound (rise, fall, arch, dip, flat, pop, click, hiss, then the three sequences; only when armed). The power-on press itself is ignored | |

- **Timing** (`config.h`): 25 ms debounce. Presses belong to one series while each starts within 400 ms (`BTN_SERIES_GAP_MS`) of the previous release; the series acts 400 ms after its last release, so a single click also waits 400 ms. A hold of 1 s or more ends a series without counting it.
- **Every state change reaches the phone** as a no-sound message (when one is subscribed), whether the button, the app or the console caused it. "Stopped" and "paused" are both `armed:false` on the wire; the difference is only local.
- **Boot:** awake and disarmed, and it stays awake until told to sleep (`VOX_BOOT_ARMED=1` boots armed).
- **Disconnect:** an unexpected disconnect disarms the device, and it stays disarmed when the phone comes back. The device stays awake; nothing puts it to sleep except the button, the app, and the two 60 s timeouts below.

**Sleep.** The device sends `{"v":1,"id":N,"mode":...,"armed":false,"sleeping":true,"sounds":[],"sequence":[]}`, waits until it has gone out (plus 300 ms), drops the link, shuts BTstack down, powers the CYW43 radio chip off (`cyw43_arch_deinit`: its power-enable pin goes low) and stops I2S (the INMP441 then sleeps by itself). The RP2350 stays in a light sleep: the CPU waits for an interrupt between 5 ms button checks (`SLEEP_POLL_MS`), and the USB console keeps working (`status` says `power: asleep`). The on-board LED is on the radio chip, so the heartbeat stops while asleep.

**Wake** (5 presses, or a 5 s hold) powers the radio back up (the console prints how long it took: `awake after N ms`; the radio firmware reload plus 0.35 s to restart the mic) and advertises.
- After **5 presses** it waits for a bonded phone. When one subscribes, the device arms, and the state-on-connect message says `armed:true`. With no phone subscribed within 60 s (`WAKE_WAIT_MS`) it sleeps again.
- After a **5 s hold** the pairing window is open; if it closes after 60 s without a new bond and no phone connected, the device sleeps again. With a phone connected it stays awake and disarmed.

**Power bank build.** `VOX_SLEEP_STAYS_AWAKE=1` (in `config.h`, or `-D` through `tools/build.sh`) turns every sleep into "disarm and stay awake": the reply is an ordinary `armed:false` state message (no `sleeping`), and the link stays up. Some power banks switch off when the draw gets small.

**Current (not measured: no meter here; estimates).**

| State | Estimate at 5 V USB | Basis |
|---|---|---|
| awake, advertising or connected, mic running | about 40–60 mA | RP2350 at 150 MHz, CYW43 BLE, INMP441 (1.4 mA) |
| asleep (this firmware) | about 15–25 mA | RP2350 still clocked at 150 MHz with USB up, idling in WFE between polls; CYW43 and mic off |
| for comparison: the SDK's `pico_low_power` figures for a Pico 2 | sleep 5.9 mA, dormant 3.3 mA, powman P-state 0.25 mA | `pico/low_power.h` table |

The light sleep was chosen because it keeps the USB console and the `btn` simulation working, and it wakes reliably from a polled button. Dormant or P-state sleep would cut the current by 5–100× but kills USB and needs a real button on a GPIO wake source: a follow-up once the button is wired and a USB power meter is at hand. Many power banks switch off below about 50–100 mA, so on a power bank even the awake draw may be too small; that is what `VOX_SLEEP_STAYS_AWAKE` is for.

**Watchdog.** If `loop()` stops for 8 s (`WATCHDOG_MS`), the chip restarts. The boot log says why it last restarted (`reset reason: ...`; `WATCHDOG` means a hang).

## Bluetooth LED

One blue LED shows **only the Bluetooth link and whether the device is awake**. Armed, paused, stopped and the mode are shown on the phone, not on the device. Timings are in `config.h`.

| LED | Meaning |
|---|---|
| slow blink: 80 ms on, once a second | awake, no phone connected: advertising |
| fast blink: 5 times a second | the pairing window is open, or a phone is connected and pairing / encrypting / subscribing is in progress |
| off | connected and subscribed (whatever the armed state or mode) |
| off | asleep |
| on / off steady | `led on` / `led off` (wiring test); `led auto` returns to the status |

A phone with a stale bond (a flash erased the device's copy) fails to encrypt: fast blink until the phone gives up, then the slow blink again.

The on-board LED blinks for 50 ms once a second while awake, as a heartbeat that shows the firmware is running.

## On-device extractor

`extract/src/` is a module-for-module C++ port of `extractor/vox_extract` (the reference; FINGERPRINT.md, vectors/README.md). It is plain C++17 with fixed buffers: no heap, no STL, nothing allocated after init. The same sources build the firmware (as an Arduino library: `build.sh` passes `--library extract`) and the PC tools.

| File | Python | What it does |
|---|---|---|
| `vx_config.*` | `config.py` | `VxConfig`, all 104 fields in the same order, same defaults (an X-macro list); `vx_config_check` refuses a config the fixed buffers cannot hold; flat JSON in and out |
| `vx_decim.*` | `resample.py` `Decimator3` | 48 → 16 kHz (firwin Kaiser taps computed at init). Not used by the mic (16 kHz); used for 48 kHz feeds |
| `vx_fft.*` | numpy `rfft` / `irfft` | a real FFT (radix-2², bit-identical to plain radix-2) for the 512-point spectrum and the 1024-point autocorrelation. arduino-pico 6.1.1 has no CMSIS-DSP; this file is the one to swap |
| `vx_frontend.*` | `frontend.py` | 60 Hz high-pass, framing, energy, zcr, centroid, flatness, flux, band ratios, MPM pitch, the fp1 per-frame sums |
| `vx_segmenter.*` | `segmenter.py` | the noise floor (blocks, start-up sub-blocks, rise limit), the gate with pre-roll and hangover, the per-sound statistics |
| `vx_classify.*` | `classify.py` | the whole decision order and the raw measurements; `vx_py_round` is Python's `round` |
| `vx_lines.*`, `vx_vocab.*` | `lines.py`, `vocab.py` | the schema lines, byte-identical; the vocabulary and its digest (`139d86bd72e13ae5`, checked against `vocab.digest()`) |
| `vx_fingerprint.*` | `fingerprint.py` | fp1 (24 values) and pitch16 |
| `vx_extractor.*` | `extractor.py` | the streaming wrapper: push / flush, the talking-train context, fp1 on every sound |
| `vx_json.*` | `Event.to_dict()` | event JSON (Python's number format) and the PROTOCOL.md `features` entry |
| `vx_real.h`, `vx_impl.h` | | `vx_real` = float (per-frame DSP), `vx_acc` = double (floor and segment sums); build settings (no fused multiply-add; -O2 and RAM placement on the Pico) |

**On the Pico** (`arduino/vox_node/ext.*`): core 0 reads I2S as before and hands every sample, quantised to int16 exactly as `mic stream` sends it (`l >> (16 - gain/6)`, 12 dB by default), to a lock-free ring (8192 samples, 512 ms). Core 1 (`setup1`/`loop1`, its own 8 KB stack) runs the extractor on the ring and puts each finished sound into a 4-entry queue; core 0 takes it from there and sends it with `send_sound` plus the `features` entry, on the device clock (the stream's first sample = `millis()` when it was queued). Nothing on core 1 prints or touches BLE. Sleep (`mic_end`) stops the stream; a wake (`mic_begin`) starts a new one from a clean state, as does `ext on`. A sound still open at sleep is dropped. BTstack's flash writes (bonds) pause core 1 through arduino-pico's `idleOtherCore`; the ring covers the pause.

Because the extractor's input is exactly the `mic stream` samples, a WAV from `tools/pico_stream.py` (same gain) replays what the device heard: `build/host/vx_cli --wav x.wav` and `extractor/run python -m vox_extract ...` give the device's events.

**Port decisions** (where the Python could be read two ways):
- The raw measurements are **rounded** (`round(x, n)`) in the reference, and later decisions read the rounded values (`sounds_like_voiced`, `speech_cues`, the talking-train context, fp1). The port rounds the same way (`vx_py_round`: correctly rounded, half to even) and decides on the rounded values.
- The vectors' `floor_db_after` column is the floor **before** the frame's own update (`Extractor.floors` appends before `seg.push`); `vx_cli --frames` writes the same.
- Precision: per-frame DSP in float32 (the M33 has a single-precision FPU); noise-floor and segment accumulators, classify and fingerprint in double (once per sound; the RP2350's double coprocessor). All-float32 accumulators (`-DVX_ACC_FLOAT`) are an option, not the default.
- Flatness and flux sum 241 per-bin logs in the reference; the port takes the log of a running product (mantissa and exponent kept apart), which is the same sum with one log per frame (same exactness, about 38 k fewer instructions per hop).
- No fused multiply-add anywhere (`vx_impl.h`): the device then rounds like the checked host build. Its libm (arduino-pico's float functions) still differs from glibc in the last bit, which the tolerances cover; `tools/ext_feed.py` checks the device itself.

### Performance and memory

Per 10 ms hop the budget is 1.5 M cycles (one core at 150 MHz). Measured without the device as **instructions** of the same code built for a Cortex-M33 (`-mfpu=fpv5-sp-d16`, the Pico's flags) under QEMU's mps2-an505 with `-icount` (`extract/host/m33/run.sh`; `PROFILE=1` splits the front end):

| | instructions | share of 1.5 M |
|---|---|---|
| hop, mean (every vector: silence, voice, music, noise) | 205 k | 14 % |
| hop, max | 234 k | 16 % |
| sound end (classify + fp1), max over the vectors | 1.94 M (talking), 1.1 M (a hum), 0.28 M (click/pop) | once per sound; the ring absorbs it |

Per hop (`PROFILE=1`): the 512-point spectrum FFT 34 k, the autocorrelation's 1024-point FFT and inverse 69 k + 58 k, centroid/flatness 8 k, flux 10 k, NSDF and peaks 10 k, energy/zcr/window 6 k, the fp1 sums 4 k. On the M33 most instructions take one cycle (loads, taken branches and FP divides more), so expect roughly 15–20 % of core 1 while listening. The real numbers come from the device: `ext stats` prints cycles per hop (mean and max, from the core's cycle counter) and per sound end, and core 1's load.

**Measured on the Pico 2 W** (2026-09-26, `tools/ext_feed.py --vectors`, all 19 vectors; `ext stats` with the mic path running):

| | cycles | share of 1.5 M |
|---|---|---|
| hop, mean (per vector) | 237–239 k (live mic path, silence: 216 k) | 16 % (14 %) |
| hop, max | 279 k (talking) | 19 % |
| sound end (classify + fp1) | 0.89 M (click) to 3.16 M (music); talking 3.06–3.13 M, a hum 2.6–2.8 M, pop/hiss 0.91–0.95 M | 0.6–2.1 hops |
| worst single 160-sample push (a hop plus a sound end) | 4.0 M (27 ms) | 2.7 hops |
| core-1 load, live mic, no sounds | 15.6 % | |

The QEMU hop count was close (about 16 % low). The sound end was **not** an upper bound: it costs about 1.6× the QEMU instruction count (3.16 M cycles against 1.94 M instructions), because the double-precision classify and fp1 code is slower on the device than the QEMU count suggests. It is still absorbed: the worst push holds core 1 for 27 ms, while the 8192-sample ring holds 512 ms (high-water mark while feeding faster than real time: 1504; ring overflow 0, event-queue drops 0).

Optimisations applied after the exact port passed (each re-checked with `check_extract.sh`): radix-2² FFT with a bit-reversal table and a copy-only first stage for zero padding (330 k → 255 k per hop, bit-identical), one log per frame for flatness and flux (→ 217 k), -O2 for the library (→ 205 k), RAM placement for the per-hop functions (not measurable in QEMU; it avoids flash-cache misses on the Pico). Not done: skipping pitch while no sound is open (it only matters for frames that end up in a sound, but the pre-roll frames would need it later), a DCT-I for the autocorrelation's inverse (−30 k), CMSIS-DSP.

Build (secure, 2026-09-26): flash 513,676 bytes (+35,736 over the firmware without the extractor), static RAM 269,992 bytes (+118,140: extractor state 40 KB, classify scratch 36 KB, ring 16 KB, FFT tables and work 8 KB, sound queue 7 KB, fp1 work 4 KB, per-hop code in RAM 7 KB), plus core 1's 8 KB stack from the heap. Core 1's deepest call chain uses about 3.5 KB of it (`-fstack-usage`).

### On the device (steps 1–3 done 2026-09-26: all 19 vectors PASS, cycles above; steps 4–7 need the mic)

1. Flash: `PORT=$(ls /dev/serial/by-id/usb-Raspberry_Pi_Pico*-if00) tools/build.sh --no-gen --upload` (always pass the Pico's by-id port: the default `/dev/ttyACM0` may be a phone), or hold BOOTSEL while plugging in and `nix run nixpkgs#picotool -- load -x build/vox_node/vox_node.ino.uf2`.
2. `status` must end with an `ext: on, features fp1, ...` line; INFO says `"fp_version":"fp1"`.
3. The extractor alone, without the mic: `eval $PY tools/ext_feed.py --vectors` (all 19 vectors; expect PASS each, and the `hop mean` / `hop max` / `sound end` cycle lines). This is the device-side exactness and the real cycle counts.
4. The mic: `mic level` must show a signal (not ALL ZEROS / CONSTANT; if it does, check the wiring before anything else). Then hum a rise near the mic with `arm` set: the console prints `ext: rise [t0..t1] hum that rises ...` and `tx id=...`.
5. Load while listening: `ext stats reset`, wait a minute with some sounds, `ext stats`: core-1 load, hop max, ring overflow (must be 0) and event queue drops (must be 0).
6. Sleep / wake: `sleep`, `wake`, then `ext stats`: the counters restart and sounds still come through.
7. Record and replay: `eval $PY tools/pico_stream.py -s 10 -o /tmp/m.wav` while making sounds (the extractor runs at the same time), then compare the console's `ext:` lines with `build/host/vx_cli --wav /tmp/m.wav` (device times are offset by the stream's start).

## BLE link

The link follows PROTOCOL.md "BLE GATT link (v1)" exactly:

- **Advertising.** Whenever the device is awake and no phone is connected. The advertised name is `VOX-XXXX`, from the last 2 address bytes (this board: `VOX-2807`). The 128-bit service UUID is in the advertisement: flags + UUID + name fill exactly 31 bytes. The name is repeated in the scan response. The interval is 100 ms.
- **Characteristics.**
  - EVENT: notify. Subscribing needs encryption.
  - CONFIG: write, with or without the long-write procedure; up to 512 bytes. Writing needs encryption.
  - INFO: read, open: `{"v":1,"fw":"0.2.2","mic":"inmp441"|"none","fp_version":"fp1"|null}`. `fp_version` is `"fp1"` while the extractor runs with features on (the default), else null. The insecure build adds `"insecure":true`. `mic` updates when the mic appears or disappears.
- **Security.** LE Secure Connections bonding, Just Works, secure-connections-only mode. The bond key size is 16.
- **Pairing window.** A new pairing is accepted only while the 60 s window is open (hold the button 5 s). Outside it the device declines the Just Works request (`pairing: Just Works request REJECTED: pairing window closed` on the console), so only phones that are already bonded get an encrypted link and can reach EVENT and CONFIG. The window closes early on a new bond. Opening it drops a connected phone; a bonded phone may reconnect while it is open.
  - "Advertises to bonded phones" (PROTOCOL.md *Waking*) is done by this gate, not by a controller accept list: Android phones use resolvable private addresses, and filtering them in the controller would need address resolution set up for every bond. A phone that is not bonded can still see the device and connect, but cannot pair, subscribe or write.
- **App commands (CONFIG)**, PROTOCOL.md *App commands* and *Replies*: `armed` (true/false) and `mode` (`gesture`/`cursor`), alone or in one write; `sleep` (only `true`); `test_sounds` (true/false). They need an encrypted link, except on the `--insecure` build, which accepts them unencrypted.
  - Every write that reaches the firmware gets **exactly one** no-sound state reply with a fresh id, even if nothing changed, and even for `{}`, a write with only unknown keys, or `test_sounds`.
  - The reply to `sleep` is the `sleeping:true` message (armed/mode in the same write are ignored and logged); the link then drops.
  - A refused write changes nothing and gets the same reply with `"rejected":"<reason>"`: `not a JSON object`, `malformed JSON`, `bad value for armed|mode|sleep|test_sounds`.
  - Unknown keys are ignored. A `v` other than 1 is logged and the write is applied anyway.
  - `armed:false` also cancels a playing canned sequence.
- **Fragment header.** Bit 7 = last fragment, bit 6 = first fragment, bits 0–5 = counter mod 64. The counter is 0 on the first notification of every connection. A fragment carries at most MTU − 4 bytes of message. The device asks for MTU 517 and also works at 23.
- **State on subscribe.** Every time the phone enables EVENT notifications, the device sends one no-sound message with its current `armed` and `mode`.
- **Message ids** start at 1 at every boot and go up by 1 for each message sent. A message that cannot be sent does not use an id: no phone subscribed, or a sound while paused.
- **Timestamps** are `millis()` since boot.
- **Messages** are at most 4096 bytes. An extractor sound carries `features` (one fp1 entry, about 350 bytes; the message is about 600 bytes, 2 fragments at MTU 517). `ext features off` leaves it out; the canned test sounds never carry it.
- **Queue.** Up to 12 messages wait while a slow link drains; beyond that a message is dropped and counted in `status`.
- **Connection interval.** The device asks for 7.5–30 ms. BlueZ settles on 18.75 ms.

## Known limitations and future work

- **A failed radio start-up still leaks, and does not recover by itself.** Wake starts the mic before the radio, which avoids the only failure seen so far (the CYW43 SPI bus never comes up on the PIO state machine and DMA channels I2S used before a sleep; see [The button, sleep and wake](#the-button-sleep-and-wake)). If a start-up fails anyway, BTstack's power-on keeps the PIO state machine and 2 DMA channels it claimed (`cyw43_deinit` skips the release while the driver is not up), BLE stays at `starting`, and only a `reboot` recovers. Planned, not built (it would cost a flash, which erases the bonds):
  1. In `ble_power_on()`, after `cyw43_arch_init`, run the bus start-up before BTstack does (`cyw43_gpio_get(&cyw43_state, 0, ...)` under the lock, a harmless read that triggers it) and record the PIO and DMA claim masks before and after.
  2. On failure, `cyw43_ll_deinit(&cyw43_state.cyw43_ll)` frees the SPI state machine, program and DMA channels (checked on the device: released attempts did not leak). Then claim exactly the ones the failed attempt used (from the mask difference), so a retry lands on fresh ones, and retry once.
  3. On success, hold the quarantined state machine and channels while awake and release them in `ble_power_off()` before `cyw43_arch_deinit`: at most 1 state machine and 2 channels, nothing accumulates.
  4. If the retry fails too: release again, skip `stack_setup()` (BTstack's own start-up is the attempt that leaks), `cyw43_arch_deinit()`, leave `s_powered` false and return false (`wake()` already prints "the radio did NOT start"); `status` says "radio failed" instead of "starting". The next wake or a `reboot` recovers.

  To test it, temporarily put the radio before the mic in `wake()` (`power.cpp`): that fails on every wake.
