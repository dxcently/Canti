# firmware: the Pico 2 W

The device half of VOX. It will listen through an I2S MEMS mic (INMP441), turn each sound into a VOX line (a C/C++ port of `extractor/vox_extract`, not written yet), and send it to the phone over Bluetooth LE, as specified in [PROTOCOL.md](../android/PROTOCOL.md) "BLE GATT link (v1)".

**Today** `vox_node` does everything except the on-device extractor:
- the full BLE link (LE Secure Connections bonding with a 60 s pairing window, fragmentation, the app commands);
- the one button, sleep and wake (Bluetooth and mic off), and the blue status LED;
- mic diagnostics;
- **canned test sounds**: real extractor lines, generated at build time by running the Python extractor on its synthetic test clips, and sent on command.

Wiring the breadboard: [HARDWARE.md](HARDWARE.md).

## Build, flash, test

```bash
cd ~/VOX/firmware
tools/build.sh --upload                 # extractor → test_sounds.h, compile, flash (secure build)
tools/build.sh --insecure --upload      # debug build: no encryption, INFO says "insecure":true
tools/build.sh                          # compile only; --no-gen skips the extractor step

PY="nix shell --impure --expr 'with import <nixpkgs> {}; python313.withPackages (p: [p.bleak p.pyserial])' -c python"
eval $PY tools/ble_check.py             # full BLE test, about 7 minutes (four 60 s timeouts); --quick: about 2 minutes
eval $PY tools/pico_stream.py -s 5 -o /tmp/mic.wav     # record the mic
stty -F /dev/ttyACM0 115200 raw -echo && cat /dev/ttyACM0 &   # plain console; type with: echo status > /dev/ttyACM0
```

- **Flashing.** `--upload` sends `bootsel` over the serial port and then flashes with `picotool`. The arduino-cli default fails on this machine: it needs `udisksctl` to mount the RP2350 drive. A blank board, or one whose firmware hangs, needs BOOTSEL held while plugging in. Then run `nix run nixpkgs#picotool -- load -x build/vox_node/vox_node.ino.uf2`.
- **The extractor step** runs `~/VOX/extractor/run python tools/gen_test_sounds.py`. It only reads `extractor/`. It fails, and writes nothing, if the extractor no longer gives the expected label for a test clip. `--check` exits 1 when the lines or the vocabulary changed.
- **Re-flashing erases bonds.** BTstack keeps its bond store inside the program image, so every flash forgets the phone. Remove "VOX-XXXX" from the phone's (or PC's) Bluetooth list, hold the button 5 s (pairing window), then connect again. Otherwise the link fails with a re-encryption error; the serial console says so. `ble forget` erases the bonds without flashing.
- **BlueZ (PC) pairing needs an agent.** Without one, BlueZ rejects the Just Works confirmation (SMP reason 0x0c). `ble_check.py` registers its own for the run and removes the bond at the end (`--keep-bond` keeps it). With `bluetoothctl`, run `agent NoInputNoOutput`, `default-agent`, then `pair <address>`.
- **Serial console:** 115200 baud (any baud rate works over USB). Commands end with a newline and are echoed as `> cmd`.

**USB permissions (NixOS).** Flashing and the serial port need access to Raspberry Pi USB devices (vendor `2e8a`). A temporary rule in `/run/udev/rules.d/70-vox-pico.rules` gives the `users` group access until the next reboot. To make it permanent, add this to the NixOS config and rebuild:
```nix
services.udev.extraRules = ''
  SUBSYSTEM=="usb", ATTR{idVendor}=="2e8a", MODE="0660", GROUP="users"
  SUBSYSTEM=="tty", ATTRS{idVendor}=="2e8a", MODE="0660", GROUP="users"
'';
```
For about 2 s after a flash, `/dev/ttyACM0` shows `root:root 0600` until udev applies the rule. That is expected.

The Arduino IDE also works (`nix run nixpkgs#arduino-ide`). In it, add the board URL from `arduino-cli.yaml` under Preferences → Additional boards manager URLs. Then pick "Raspberry Pi Pico 2W" and set Tools → IP/Bluetooth Stack to "IPv4 + Bluetooth".

## Pins

| Signal | GPIO | Physical pin | Goes to |
|---|---|---|---|
| The button | GP14 | 19 | button → GND (internal pull-up) |
| Bluetooth LED (blue) | GP13 | 17 | 100 Ω → LED anode (long leg); cathode → GND; active high |
| Mic BCLK (SCK) | GP18 | 24 | INMP441 SCK |
| Mic WS | GP19 | 25 | INMP441 WS |
| Mic data | GP20 | 26 | INMP441 SD |
| 3.3 V | 3V3(OUT) | 36 | INMP441 VDD. **3.3 V only; never 5 V (VBUS pin 40, VSYS pin 39)** |
| GND | GND | 3, 8, 13, 18, 23, 28, 33, 38 | INMP441 GND and L/R, the button, the LED cathode |

GP11, GP12 and GP15 (pins 15, 16, 20) are free: earlier drafts had an RGB LED and a second button there.

The I2S format is 16 kHz, 64 BCLK per frame (32-bit slots, left channel), with 24-bit data from the INMP441. GP20 has a pull-down, so a missing mic reads as all zeros. INFO then says `"mic":"none"`.

## The button, sleep and wake

> **Not yet verified on hardware.** The one-button, sleep/wake and pairing-window code builds, but hasn't run on a Pico yet. An early sleep test hung the device: `cyw43_arch_deinit()` ran before BTstack had finished halting HCI. `ble_power_off()` now waits for `HCI_STATE_OFF` first, and an 8 s watchdog is the backstop. Still to do: flash, about 10 sleep/wake cycles (`btn hold 1200`, `btn clicks 5`, then check `status` says advertising), and a full `tools/ble_check.py` run.

One button, as in PROTOCOL.md "The button":

| Press | Awake | Asleep |
|---|---|---|
| 5 quick presses | armed: turn off (disarm, the `sleeping` message, sleep). Not armed: arm | wake; arm once a bonded phone subscribes |
| 1 click | gesture ⇄ cursor mode | nothing |
| hold 1 s | disarm at once, while still held (the fast stop); sleep on release | nothing |
| hold 5 s | disarm (at 1 s), then open the 60 s pairing window instead of sleeping | wake and open the pairing window |
| 2–4 presses (6 or more too) | nothing | nothing |
| held while plugging in | the **test-sound trigger**: from then on, 2 presses send the next canned sound (rise, fall, arch, dip, flat, pop, click, hiss, then the three sequences; only when armed). The power-on press itself is ignored | |

- **Timing** (`config.h`): 25 ms debounce. Presses belong to one series while each starts within 400 ms (`BTN_SERIES_GAP_MS`) of the previous release; the series acts 400 ms after its last release, so a single click also waits 400 ms. A hold of 1 s or more ends a series without counting it.
- **Every state change reaches the phone** as a no-sound message (when one is subscribed), whether the button, the app or the console caused it. "Stopped" and "paused" are both `armed:false` on the wire; the difference is only local.
- **Boot:** awake and disarmed, and it stays awake until told to sleep (`VOX_BOOT_ARMED=1` boots armed).
- **Disconnect:** an unexpected disconnect disarms the device, and it stays disarmed when the phone comes back. The device stays awake; nothing puts it to sleep except the button, the app, and the two 60 s timeouts below.

**Sleep.** The device sends `{"v":1,"id":N,"mode":...,"armed":false,"sleeping":true,"sounds":[],"sequence":[]}`, waits until it has gone out (plus 300 ms), drops the link, shuts BTstack down, powers the CYW43 radio chip off (`cyw43_arch_deinit`: its power-enable pin goes low) and stops I2S (the INMP441 then sleeps by itself). The RP2350 stays in a light sleep: the CPU waits for an interrupt between 5 ms button checks (`SLEEP_POLL_MS`), and the USB console keeps working (`status` says `power: asleep`). The on-board LED is on the radio chip, so the heartbeat stops while asleep.

**Wake** (5 presses, or a 5 s hold) powers the radio back up (the console prints how long it took: `awake after N ms`; the radio firmware reload plus 0.35 s to restart the mic) and advertises.
- After **5 presses** it waits for a bonded phone. When one subscribes, the device arms, and the state-on-connect message says `armed:true`. With no phone subscribed within 60 s (`WAKE_WAIT_MS`) it sleeps again.
- After a **5 s hold** the pairing window is open; if it closes after 60 s without a new bond and no phone connected, the device sleeps again. With a phone connected it stays awake and disarmed.

**Power bank build.** `VOX_SLEEP_STAYS_AWAKE=1` (in `config.h`, or `-D` through `tools/build.sh`) turns every sleep into "disarm and stay awake": the reply is an ordinary `armed:false` state message (no `sleeping`), and the link stays up. Some power banks switch off when the draw gets small.

**Current (not measured: no meter here; estimates).**

| State | Estimate at 5 V USB | Basis |
|---|---|---|
| awake, advertising or connected, mic running | about 40–60 mA | RP2350 at 150 MHz, CYW43 BLE, INMP441 (1.4 mA) |
| asleep (this firmware) | about 15–25 mA | RP2350 still clocked at 150 MHz with USB up, idling in WFE between polls; CYW43 and mic off |
| for comparison: the SDK's `pico_low_power` figures for a Pico 2 | sleep 5.9 mA, dormant 3.3 mA, powman P-state 0.25 mA | `pico/low_power.h` table |

The light sleep was chosen because it keeps the USB console and the `btn` simulation working, and it wakes reliably from a polled button. Dormant or P-state sleep would cut the current by 5–100× but kills USB and needs a real button on a GPIO wake source: a follow-up once the button is wired and a USB power meter is at hand. Many power banks switch off below about 50–100 mA, so on a power bank even the awake draw may be too small; that is what `VOX_SLEEP_STAYS_AWAKE` is for.

**Watchdog.** If `loop()` stops for 8 s (`WATCHDOG_MS`), the chip restarts. The boot log says why it last restarted (`reset reason: ...`; `WATCHDOG` means a hang).

## Bluetooth LED

One blue LED shows **only the Bluetooth link and whether the device is awake**. Armed, paused, stopped and the mode are shown on the phone, not on the device. Timings are in `config.h`.

| LED | Meaning |
|---|---|
| slow blink: 80 ms on, once a second | awake, no phone connected: advertising |
| fast blink: 5 times a second | the pairing window is open, or a phone is connected and pairing / encrypting / subscribing is in progress |
| off | connected and subscribed (whatever the armed state or mode) |
| off | asleep |
| on / off steady | `led on` / `led off` (wiring test); `led auto` returns to the status |

A phone with a stale bond (a flash erased the device's copy) fails to encrypt: fast blink until the phone gives up, then the slow blink again.

The on-board LED blinks for 50 ms once a second while awake, as a heartbeat that shows the firmware is running.

## Serial commands

| Command | What it does |
|---|---|
| `help` | the list below |
| `status` | state, mode, last id, power (awake/asleep, pairing window, wake wait), BLE link (MTU, interval, encryption, LESC, bond, stored bonds), mic |
| `arm`, `pause`, `stop` | set the armed state; each sends a no-sound message. `arm` is refused while asleep |
| `mode gesture`, `mode cursor`, `mode` | set or toggle the mode |
| `btn click`, `btn clicks <1..12>`, `btn hold <ms>` | press the button for you, through the same state machine as the real button: e.g. `btn clicks 5`, `btn hold 1200` (fast stop, sleep on release), `btn hold 5500` (pairing window). The real button still works at the same time |
| `sleep` | sleep now, exactly as CONFIG `sleep` does |
| `wake` | wake without arming and without the 60 s timeout (a test helper; the button's wakes behave as in the table above) |
| `buttons` | the real button's level (`PRESSED` / `released`) and the state machine (wiring test) |
| `list` | canned sounds and sequences, with the extractor digest |
| `send <sound>` | send one canned sound now, e.g. `send rise`. Its timing ends now and starts one duration earlier. Only sent when armed |
| `seq <a> <b> [<c>] [gap]` | several sounds as **separate** messages, `gap` ms apart on the device clock (default 250); each is sent when it ends |
| `seq clickpop`, `seq poppop`, `seq riserise` | the canned sequences (click→pop 260 ms from a real clip, pop→pop 250 ms, rise→rise 900 ms, which the phone should split) |
| `pad <bytes>` | a no-sound message padded with JSON whitespace up to `bytes` (maximum 4096), for fragmentation tests |
| `test on`, `test off` | the test-sound trigger (2 presses send the next canned sound) |
| `mic level` | about 10 lines a second: rms/peak/DC in dBFS, or ALL ZEROS / CONSTANT / wrong channel. Refused while asleep |
| `mic stream` | binary PCM16 frames over USB (use `tools/pico_stream.py`); `mic off` stops it |
| `mic gain <0,6,12,18,24>` | gain for `mic stream` (default 12 dB) |
| `ble` | link details |
| `ble mtu <23..517>` | the largest MTU accepted on the **next** connection (`ble disconnect` to apply now) |
| `ble disconnect`, `ble forget` | drop the link; erase every stored bond (awake only) |
| `led on`, `led off`, `led auto` | force the blue LED on or off (wiring test); back to the automatic pattern |
| `reboot`, `bootsel` | restart; restart into the USB bootloader |

## BLE link

The link follows PROTOCOL.md "BLE GATT link (v1)" exactly:

- **Advertising.** Whenever the device is awake and no phone is connected. The advertised name is `VOX-XXXX`, from the last 2 address bytes (this board: `VOX-2807`). The 128-bit service UUID is in the advertisement: flags + UUID + name fill exactly 31 bytes. The name is repeated in the scan response. The interval is 100 ms.
- **Characteristics.**
  - EVENT: notify. Subscribing needs encryption.
  - CONFIG: write, with or without the long-write procedure; up to 512 bytes. Writing needs encryption.
  - INFO: read, open: `{"v":1,"fw":"0.1.0","mic":"inmp441"|"none","fp_version":null}`. The insecure build adds `"insecure":true`. `mic` updates when the mic appears or disappears.
- **Security.** LE Secure Connections bonding, Just Works, secure-connections-only mode. The bond key size is 16.
- **Pairing window.** A new pairing is accepted only while the 60 s window is open (hold the button 5 s). Outside it the device declines the Just Works request (`pairing: Just Works request REJECTED: pairing window closed` on the console), so only phones that are already bonded get an encrypted link and can reach EVENT and CONFIG. The window closes early on a new bond. Opening it drops a connected phone; a bonded phone may reconnect while it is open.
  - "Advertises to bonded phones" (PROTOCOL.md *Waking*) is done by this gate, not by a controller accept list: Android phones use resolvable private addresses, and filtering them in the controller would need address resolution set up for every bond. A phone that is not bonded can still see the device and connect, but cannot pair, subscribe or write.
- **App commands (CONFIG)**, PROTOCOL.md *App commands* and *Replies*: `armed` (true/false) and `mode` (`gesture`/`cursor`), alone or in one write; `sleep` (only `true`); `test_sounds` (true/false). They need an encrypted link, except on the `--insecure` build, which accepts them unencrypted.
  - Every write that reaches the firmware gets **exactly one** no-sound state reply with a fresh id, even if nothing changed, and even for `{}`, a write with only unknown keys, or `test_sounds`.
  - The reply to `sleep` is the `sleeping:true` message (armed/mode in the same write are ignored and logged); the link then drops.
  - A refused write changes nothing and gets the same reply with `"rejected":"<reason>"`: `not a JSON object`, `malformed JSON`, `bad value for armed|mode|sleep|test_sounds`.
  - Unknown keys are ignored. A `v` other than 1 is logged and the write is applied anyway.
  - `armed:false` also cancels a playing canned sequence.
- **Fragment header.** Bit 7 = last fragment, bit 6 = first fragment, bits 0–5 = counter mod 64. The counter is 0 on the first notification of every connection. A fragment carries at most MTU − 4 bytes of message. The device asks for MTU 517 and also works at 23.
- **State on subscribe.** Every time the phone enables EVENT notifications, the device sends one no-sound message with its current `armed` and `mode`.
- **Message ids** start at 1 at every boot and go up by 1 for each message sent. A message that cannot be sent does not use an id: no phone subscribed, or a sound while paused.
- **Timestamps** are `millis()` since boot.
- **Messages** are at most 4096 bytes. `features` is left out: fp1 is not final.
- **Queue.** Up to 12 messages wait while a slow link drains; beyond that a message is dropped and counted in `status`.
- **Connection interval.** The device asks for 7.5–30 ms. BlueZ settles on 18.75 ms.
